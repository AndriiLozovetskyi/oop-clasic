# Server managment


## Лабораторна робота №1 Фабричний метод
Коли з'являється багато серверів, для розділення на класи, було б непогано реалізувати розділення по типу.
Для цього може знадобитися виконання фабрики.
Отже, створюємо клас ServerFactory. Він буде містити метод create_server, який, на основі типу сервера, буде створювати відповідний сервер, із відповідними системними х-ми.
Відповідно, метод create_server, приймає тип сервера, його назву, та конфігурація, яка побудована на основі прототипу.
Завдання

Створити клас ServerConfig, який описує конфігурацію сервера.

Поля класу:
os_name — назва операційної системи
cpu — кількість CPU
ram — обсяг RAM
Вимоги:
Реалізувати метод clone(), який створює повну копію об’єкта
Після клонування об’єкт можна змінювати без впливу на оригінал

##  Лабораторна робота №2 Прототип
Для реалізації керування серверів, існує потреба їх створити.
Для цього реалізовується відповідний класи, які описують технічні характеристики віртуальних машин. 
Щоб побудувати базову віртуальну машину, потрібно реалізувати класи.
Для цього будемо використовувати патерн прототип. Створимо клас ServerConfig, який буде містити поля:
- назву ОС
- CPU
- RAM

Але щоб спростити керування віртуальними машинами, і з нуля не створювати нову, для іншої задачі, використовувати патерт прототип,
який дозволяє легко копіювати клас, після цього модифікувати його.
Завдання

Створити клас ServerFactory.

Метод:
create_server(server_type: str, name: str, config: ServerConfig)
Вимоги:
Фабрика створює сервери різних типів (наприклад: web, db, cache)
Кожен тип має свої дефолтні налаштування (CPU/RAM/OS можуть відрізнятись)
Використовується конфігурація, створена через Prototype
Очікування:
Не створювати сервери напряму через ServerConfig
Вся логіка створення — у фабриці


##  Лабораторна робота №3 Стратегія
Так як, у нас є потрібні сервера, нам потрібно їх створити.
Для цього, за допомогою terraform, потрібно створити віртуальні машини, після чого їх налаштувати за допомогою ansible.

Для цього підійте патерн Стратегія. Створююємо клас DeployStrategy, який буде мати метод, deploy, який потрібно буде реалізувати в класах нащадках.
Реалізовуємо також AnsibleDeploy та TerraformDeploy, 
Кожен клас має свою реалізацію методу deploy, який по своємо виконує операцію

Також, нам потрібно клас DeploymentContext, який буде приймати відповідну стратегію, та запускати метод deploy.
Завдання

Реалізувати систему деплою.

Інтерфейс:
class DeployStrategy:
    def deploy(self, server): ...
Реалізації:
TerraformDeploy
AnsibleDeploy
Додатково:
Створити DeploymentContext
Він приймає стратегію через конструктор
Викликає deploy()

## Лабораторна робота №4 Макрокоманди
Необхідно реалізувати механізм пакетного виконання інфраструктурних операцій. 
Підсистема повинна дозволяти динамічно формувати чергу (пайплайн) з атомарних команд та виконувати їх одним викликом, 
використовуючи патерн Macro Command.

Потрібно реалізувати метод базовий клас Command, який має метод execute. 
На основі нього, створимо класи StartServerCommand, BackupServerCommand, з свою реалізацією.
Клас MacroCommand, який наслідується від Command, який містить метод add_command, який додає до списку команд, які потрібно виконати.
Метод execute, виконує усі команди по черзі.
Завдання

Додати моніторинг і розширення функціоналу серверних операцій.

Базовий клас:
class BasicServerOperation:
    def operate(self): ...
Декоратор:
Базовий клас-декоратор, який приймає BasicServerOperation
Реалізація:
PrometheusExporterDecorator

## Лабораторна робота №5 Ітератор
Необхідно реалізувати модуль інвентаризації серверів, який надає стандартний, уніфікований інтерфейс для послідовного 
обходу (перебору) всіх об'єктів серверів у колекції, використовуючи патерн Iterator та вбудований протокол ітерації Python.

Потрібно стоврити клас ServerInventory. Метод add_server, в який будуть додавати ноди.
Та реалізувати магічні методи __iter__ та __next__, які допоможуть проходитися по об'єктам в циклі.

Потрібно реалізувати програмний компонент (Адаптер) який забезпечить сумісність між існуючим клієнтом для опитування legacy-обладнання 
(LegacyDeviceClient) та стандартним інтерфейсом збору метрик (PrometheusCollectorInterface).

Проблема в тому, що в нас є старий логер, але який має підтримувати новий спосіб логування.
Завдання

Забезпечити сумісність між legacy та новим інтерфейсом метрик.

Є:
LegacyDeviceClient (старий інтерфейс)
PrometheusCollectorInterface (новий стандарт)
Потрібно:

Створити клас-адаптер, який:

приймає LegacyDeviceClient
реалізує PrometheusCollectorInterface

## Лабораторна робота №6 Інтерпретатор

Необхідно реалізувати програмний модуль (Engine), який дозволяє оцінювати складні логічні вирази (правила фільтрації) 
щодо об'єктів конфігурації серверів. 
Модуль повинен будувати Абстрактне Синтаксичне Дерево (AST) за допомогою патерна Interpreter для обчислення результату в runtime.
Завдання

Реалізувати механізм snapshot/rollback для віртуальної машини.

Компоненти:
ServerState (memento)
VirtualMachine (originator)
StateManager (caretaker)
Вимоги:
VM може створювати snapshot
VM може відновлювати стан зі snapshot
Внутрішній стан VM не повинен бути доступний напряму

## Лабораторна робота №7 Моменто
Необхідно реалізувати механізм створення знімків стану віртуальної машини (ВМ) та відкату до них у разі збою 
(наприклад, після невдалого оновлення ядра або конфігурації). 
Підсистема повинна базуватися на патерні Memento, щоб забезпечити безпечне збереження стану без порушення інкапсуляції самої ВМ.
Завдання

Реалізувати систему команд для інфраструктури.

Базовий клас:
class Command:
    def execute(self): ...
Реалізації:
StartServerCommand
BackupServerCommand
